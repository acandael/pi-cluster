# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Flux CD GitOps repository for a Raspberry Pi Kubernetes cluster. There is no code to build or test — the "source of truth" is the YAML in this repo; Flux running in the cluster reconciles it. Changes are deployed by committing to `main` and letting Flux pull (`ssh://git@github.com/acandael/pi-cluster`, branch `main`, 1-minute interval).

## Repository layout (the big picture)

```
clusters/staging/         # Flux entry point for the "staging" cluster
  flux-system/            # Bootstrap manifests (DO NOT EDIT — generated by `flux bootstrap`)
  apps.yaml               # Flux Kustomization → ./apps/staging (with SOPS decryption)
  monitoring.yaml         # Flux Kustomization → ./monitoring/controllers/staging
  .sops.yaml              # Age recipient + encrypted_regex for `data`/`stringData`

apps/
  base/<app>/             # Plain manifests, app-agnostic to environment
  staging/<app>/          # Overlay: kustomization.yaml references ../../base/<app> + env extras (secrets, ingress)

monitoring/
  controllers/base/<chart>/      # HelmRepository + HelmRelease + namespace
  controllers/staging/<chart>/   # Overlay binding the release to a namespace
  configs/                       # (currently empty — reserved for dashboards/alerts)
```

Reconciliation chain: `flux-system` Kustomization (path `./clusters/staging`) → picks up `apps.yaml` and `monitoring.yaml` → those Kustomizations point at the staging overlay paths → kustomize composes base + overlay → Flux applies.

When adding a new app: create `apps/base/<name>/` with `namespace.yaml`, the workload, a `kustomization.yaml`, then `apps/staging/<name>/kustomization.yaml` referencing `../../base/<name>/`. No edit to `apps.yaml` is needed — the staging Kustomization recursively picks up everything under `apps/staging/`, but each subdirectory needs its own `kustomization.yaml`.

## Secrets (SOPS + age)

- Encryption is mandatory for any `Secret` resource committed here. `.sops.yaml` matches `*.yaml` and encrypts only `data` and `stringData` fields, leaving the rest of the manifest readable.
- The single recipient is `age19ah6j55kkkecmcjakhjnj7xel0p8s9qegzphghj45jp7n20lqpnsrzw2gp`. The matching private key lives in the cluster as the `sops-age` secret in `flux-system` namespace — referenced by `clusters/staging/apps.yaml` (`spec.decryption`). The private key is NOT in this repo.
- The `monitoring` Flux Kustomization currently has `decryption` commented out — if you add a SOPS-encrypted secret under `monitoring/`, uncomment that block in `clusters/staging/monitoring.yaml` or move the secret under `apps/`.
- Encrypt with: `sops --encrypt --in-place <file>.yaml` (sops auto-discovers `.sops.yaml`). Decrypt to inspect: `sops --decrypt <file>.yaml`.
- The age private key must be available locally (e.g. `SOPS_AGE_KEY_FILE`) to encrypt new secrets matching the existing recipient.

## Common commands

```bash
# Validate kustomize output locally before committing
kustomize build apps/staging/linkding
kustomize build monitoring/controllers/staging/kube-prometheus-stack

# Force Flux to reconcile immediately instead of waiting for the interval
flux reconcile source git flux-system
flux reconcile kustomization apps
flux reconcile kustomization monitoring-controllers

# See what Flux thinks is wrong
flux get kustomizations -A
flux get helmreleases -A
kubectl -n flux-system logs deploy/kustomize-controller

# Inspect deployed apps
kubectl -n linkding get all
kubectl -n monitoring get all
```

## Conventions to follow

- App overlays set `namespace:` at the kustomization level (see `apps/staging/linkding/kustomization.yaml`) rather than on every manifest — base manifests omit `metadata.namespace`.
- Linkding is exposed publicly via a `cloudflared` tunnel deployment, not an Ingress. The tunnel name (`ldpi`) and hostname mapping live in the ConfigMap inside `apps/staging/linkding/cloudflare.yaml`; tunnel credentials live in the encrypted `tunnel-credentials` secret. New publicly-exposed services follow the same pattern (add an ingress rule to that ConfigMap).
- Helm-based components go under `monitoring/controllers/` (or follow the same pattern elsewhere) as `HelmRepository` + `HelmRelease` pairs — not via `helm install`. Versions are pinned in the `HelmRelease`.
